## 1. 链式漂移：25 段之后画面会崩

### 现象

按"每段用上一段末帧做首帧"的方式逐段生成，25 段拼成 3 分半的片子后：

| 时间点 | 画面状态 | 实测亮度 |
|---|---|---|
| 10s | 正常 | 147 |
| 40s | 略暗 | 124 |
| **70s** | **开始崩**（肤色偏红、噪点） | 107 |
| 100s | 明显劣化（脸型开始变形） | 87 |
| 130s | 严重（五官扭曲） | 71 |
| 160s | 崩坏（色斑、噪点） | 58 |
| 190s | 几乎不可用 | 52 |
| 212s | 彻底崩 | 48 |

**亮度单调递减，从 147 掉到 48**，同时伴随噪点增加与面部结构漂移。

### 根因

每段生成都会引入微小误差（色偏、噪声、面部结构的微小位移）。下一段以它为起点，**误差被当成"真实输入"继续放大**。

这是链式结构的固有性质，不是参数没调好。

**为什么之前没发现**：只测 2-3 段时，累积量在可接受范围内（4 段内画面仍然正常）。**必须跑到 10 段以上才会暴露。**

### 错误解法（我试过的）

| 尝试 | 结果 |
|---|---|
| 后处理做逐帧亮度拉平 | 段内波动能压平（标准差 1.45 → 0.21），但**噪点与面部变形校正不了** |
| 交叉淡化接缝 | 掩盖了接缝，掩盖不了整体崩坏 |
| 提高采样步数 | 减缓但不能阻止累积 |

### 正确解法：双重身份约束

MiniMax H3 的 `MiniMaxH3LongVideoInNodeLoopEffectsT8Advanced` 有两个参数专门为此设计，**默认值会让你踩坑**：

```python
# ❌ 默认配置（会崩）
first_frame_reuse = "segment0_only"        # 只有第 1 段用参考图，之后全靠末帧链
persistent_identity_strategy = "single_reference"
persistent_identity_image = None           # 没接

# ✅ 正确配置
first_frame_reuse = "persistent_identity_reference"
persistent_identity_strategy = "scene_plus_identity"
persistent_identity_image = <原图的脸上半身裁剪>   # 必须接！
```

**源码里的判据**（`h3_t8/long_video.py`）：

```python
"persistent_identity_image was ignored because first_frame_reuse is segment0_only"
```

也就是说：**`segment0_only` 会让防漂移机制直接失效**，即使你接了图也不生效。

**双重约束的作用机制**：

- `first_frame`（上一段末帧）→ 保持**连贯性**
- `persistent_identity_image`（原图）→ 持续把画面**拉回原始外观**

两个约束互相拉扯，漂移被压住。

> ⚠️ **待实测**：这个配置组合是读源码得出的，尚未跑完整 25 段验证。如果仍然漂移，退路是**每 3-4 段用原图重置一次首帧**（代价是重置点有轻微跳变）。

## 2. 拼接会出现重复帧

**现象**：用 `first_frame` 强制衔接时，下一段的首帧就是上一段的末帧，硬拼起来**重复一帧**，观感是"顿一下"。

**解法**：拼接时裁掉每段的第 0 帧（视频与音频同裁）。

```bash
ffmpeg -i seg.mp4 -vf "select='gte(n\,1)',setpts=N/24/TB" \
       -af "atrim=start=0.0417,asetpts=N/SR/TB" out.mp4
```

## 3. 亮度会逐段递减（即使不崩）

即使画面结构没崩，**每段的整体曝光也会差 3-6 个点**，且方向是**单调变暗**。

**原因**：每段独立采样，模型对"这段该多亮"没有绝对基准。

**能做的**：

- 段内逐帧拉平（乘性增益 + 时域平滑）可以把标准差从 1.45 压到 0.21
- **段间落差压不平**（用 `cosine_bridge` 只能平滑过渡）

**结论**：这是分段生成的固有代价，除非用节点内循环（latent 续接）而不是像素拼接。

## 4. 台词字数决定成败

**实测**：10.8 秒 ≈ **40 个汉字**（3.7 字/秒）。

| 字数 | 结果 |
|---|---|
| 太少（30 字） | 说完还剩时间，**模型自己往后编**（会编成英文或无意义音节） |
| 刚好（40 字） | 正好填满 |
| 太多（50 字） | 说不完，尾部被截断 |

**所以宁可多写 4-6 字，不要少写**——截断只是缺几个字，自编是内容错了。

**语速不可控**：没有语速参数。同样 40 字，撒娇句会拖慢（3.4 字/秒），吐槽句会连珠炮（4.5 字/秒），**同一工作流两段能差 1.5 秒**。

## 5. 不要喂唱歌的音频当音色参考

**踩过的坑**：拿一首歌的人声做 `ref_audios`（音色参考），想让它"模仿这个音色"。

**结果**：它把歌的**唱腔**也学走了——明明是说话场景，说出来的每个字都带着旋律，听起来像"唱着说"。

**原因**：H3 的音频参考学的不只是音色，还有**发声方式**。

**正确做法**：

- **说话场景**：不接参考音频，纯文字描述音色（"二十出头、清亮偏暖、语速自然"）
- **或**：接一段**正常说话的录音**
- **绝不要**接唱歌的音频

## 6. 间奏段会"念出训练数据里的水印"

**现象**：让模型生成"不说话、只微笑摇晃"的间奏段，它偶尔会发出：

```
"字幕by索兰娅"
```

**这是训练数据里视频字幕的文本**，被模型当成了"这种画面该配的语音"。

**还踩过的反向坑**：在 prompt 里写 `DO NOT say any words, DO NOT read any caption, DO NOT pronounce subtitles...`，**结果反而更容易触发**——提到"字幕/水印"这些词本身就在激活那些概念。

**正确做法**：

- **prompt 只写正向动作**，不提"文字、字幕、水印"任何一个词
- 验证时把这类词加进黑名单（水印词 + 字数上限 6 + 纯气声判定）
- **兜底**：3 次重试仍失败，用**静帧（轻微平移/缩放）**合成该段，保证零语音

## 7. 依赖链上的其他坑

### whisper

- **必须 CPU int8 跑**：GPU 会报 `cublas64_12.dll not found`（torch cu130 用的是 cublas 13）
- **不能直接传 wav 路径**：PyAV 版本不兼容会报 `metadata_errors` 参数错
- **解法**：用 `wave` 读成 numpy 数组再喂

### 相似度比对

**字符级比对会误判**：whisper 对唱歌的输出经常是**繁体 + 同音错字**。

```
目标: 牵牵手就像旅游，成千上万个门口
转写: 牽牽手就像旅遊趁牽上萬個門口
字符相似度: 0.714  ❌ 被误判为不合格
拼音相似度: 0.990  ✅ 正确判定
```

**必须用拼音级**（`pypinyin` + `difflib.SequenceMatcher`）。

### 帧数约束

- `render_window_frames` **必须在 17n+5 网格**（124、141、158、175、192、209、226、243、260...）
- **最小值 124**（56 帧会被拒绝：`Value 56 smaller than min of 124`）
- `context_frames` **只接受 5 / 22 / 39**（填 34 会报错）

### chain_id

**每次改配置都必须换新的 `chain_id`**，否则：

```
This chain_id contains accepted segments from a different in-node effects contract
```

或

```
resume_existing is false but this chain_id already contains saved state
```

## 8. 长任务的工程坑

### `Select-Object -First N` 会杀掉上游进程

在 PowerShell 里这样跑长任务：

```powershell
python long_task.py 2>&1 | Select-Object -First 100
```

**满 100 行后管道关闭，python 进程被终止**。一个跑了 4 小时的任务就这么没了。

**解法**：让脚本自己写日志文件，不要用 `Select-Object` 截断。

### 断点续跑必须有

逐段生成动辄 6-7 小时，中途断一次就前功尽弃。

**做法**：维护 `state.json` 记录已完成段与上一段末帧，重启时跳过已完成部分。

### 降级必须留退路

某段反复失败不该让整条流程中止。**策略**：

- 唱段：重试 N 次后降级使用最后一版，并标记为问题段
- 间奏段：重试后改静帧兜底
- **记下失败段编号**，方便后续单独重跑
